# Implementation profiles

How each kind of stack meets the technology-neutral rules of the rulebook, mainly R8.1
(data models), R8.5 (an offering reaches only the data it defines) and R8.6 (minimum
security baseline). The rulebook says *what* must hold; this page says *how* for each
stack. A participant with a different stack adds its profile here before its offerings
are published.

Profiles do not name participants. Each participant keeps the **evidence** of its own
conformance (its datasets, deployed versions, checks run and their results, known
non-conformities) in its own repository, and the operator reviews it (R8.7). For the
connectors the operator deploys, that is `CONFORMANCE.md` in dataspace-on-upv.

## Background: why the request is not enough

The policy engine (odrl-pap → OPA) decides **before** the request reaches the data, so it
can only check what the consumer wrote in the request: the path, the `?type=` parameter,
the type inside an `urn:ngsi-ld:<type>:<id>` id. Any part of the data's location that a
policy does not check, and that the consumer can choose, must be fixed by the
connector. Otherwise an offering for one type reaches every collection that holds that
type (see [enforcement-capabilities](enforcement-capabilities.md)).

## Gateway baseline (every stack)

| Requirement | How it is met |
|---|---|
| R8.6: only the needed endpoints | Data routes match only the entity endpoints (`/ngsi-ld/v1/entities`, `/ngsi-ld/v1/entities/*`), GET only. |
| R8.6: no consumer-chosen tenant | The gateway removes `NGSILD-Tenant` (and `Fiware-Service`, `Fiware-ServicePath` in front of NGSI-v2), or fixes them server side. |
| R8.6: trusted values removed | The gateway removes `X-Stripped-Path`, which odrl-pap would otherwise take as the request path. |
| R7.5: fair use | Request limit per buying organisation (issuer of its credential) on each offer route, with the values generated by this repository. |

## NGSI-v2 platform behind a translator (Lepus)

NGSI-v2 platforms are reached through Lepus, which translates NGSI-LD requests: the
NGSI-LD tenant becomes `Fiware-Service`, and the scope filter (`scopeQ`) becomes
`Fiware-ServicePath`. A platform usually publishes one collection per servicePath, and
the same entity type can live in several of them, some of which are not offered.

| Requirement | How it is met |
|---|---|
| R8.5: only the offered collection | Lepus serves only the servicePaths listed for each type in its map (`lib/entityServicePaths.js` in CitComAI-Hub/lepus, v1.4 or later). `scopeQ` naming any other one gets 400. A new servicePath on the platform is not served until it is added to the map on purpose. |
| R8.5: only the offered type | Lepus makes the platform enforce the type the policy checked, including the one written in an entity id (v1.3 or later). |
| R8.1: data models | NGSI-v2 data is often not Smart Data Models-conformant as published (null attributes, numbers as strings, local codes). Lepus v1.6 or later adapts known cases without inventing data (`lib/sdmConformance.js`). The provider audits what consumers get with `tools/sdm-audit/` in the fork, against pinned SDM schemas, and declares what cannot be fixed without inventing data (for example, a required location that the source does not have). |

If two collections of the same type must become **different** offerings (or one of them
stays internal while the other is offered), a type-based policy cannot tell them apart.
Then each collection gets its own gateway path (for example
`/lepus/<collection>/ngsi-ld/…`), the gateway fixes the collection server side, and
the policy checks that path.

## Native NGSI-LD broker (Orion-LD, Scorpio)

| Requirement | How it is met |
|---|---|
| R8.5: only the offered collection | Keep each offered collection in its own tenant, or use scopes and make sure the consumer cannot reach a scope or tenant that is not offered (the gateway fixes or removes `NGSILD-Tenant`; `scopeQ` is restricted or the broker holds only offered data). |
| R8.1: data models | The provider loads the data already in Smart Data Models form and audits it against the pinned SDM schema of each type. |

## Web services

| Requirement | How it is met |
|---|---|
| R8.5 | Each service has its own path and policy. If several services share a host (and its session cookie), OPA still decides on every request. |
| R8.6 | Gateway baseline above, minus the data-route rules. |
